01

算力該花在哪：從訓練搬到推論

▶ 00:00:05
一句話重點

過去 LLM 的進步幾乎都來自訓練階段；test-time scaling 把同一筆預算搬到「回答問題的那一刻」，模型參數完全不動。

講者先回顧上一講的三步驟。Pre-training 歷時數月、動輒成千上萬張 GPU；接著是 fine-tuning；最後才是推理。長久以來，「讓模型更強」等於「在訓練時投入更多資料與算力」，而每次推理的成本相對可以忽略——因為那本來就是一問一答、來回一次的事。

誰負擔模型開發者模型開發者或領域團隊每次使用的人

這個轉變的實務意義是：算力從「一次性、由少數人負擔」變成「按需、每次都可追加」。講者特別提到，推論算力還可以安排成離線的長工作——把 agent 放出去解題，讓它持續產生 token、持續改善答案的品質，最後再交付結果。

這堂課的核心張力：多花算力確實能產生更多、更好的候選，但「產生很多候選」和「知道哪個候選是對的」是兩件完全不同的事。整堂課就是圍繞這個落差展開：前半段講怎麼把正解生成出來，後半段講怎麼把它認出來，以及當認不出來時，該怎麼把有限的算力花在刀口上。
02

Repeated Sampling：問很多次，總有一次對

▶ 00:01:12
一句話重點

同一題問 k 次，只要其中一次答對就算成功。單題成功率 1−(1−p)k 隨 k 指數上升，但代價是取樣次數呈指數成長。

課堂用「無限猴子定理」破題：讓猴子在打字機前一直敲，總有一天敲出莎士比亞。〈Large Language Monkeys〉把 LLM 當成那隻猴子——模型對同一個問題本來就會給出不同答案，那麼多問幾次，就有機會碰到那個平時問不到的正確答案。

做法只有兩步，但兩步的難度完全不同：

第一步

生成：把候選集合擴大

即使單次回答不可靠，只要候選裡有正解，就還有機會。這一步只看 coverage（也等同 pass@k）：一題的 k 個樣本裡至少有一個是對的。

第二步

辨識：把正解挑出來

系統要能從所有候選中辨認出正確的那一個。這一步靠 verifier 或某種選擇機制，也正是第 05 節的主題。

動手試試：單次正確率 p 與取樣數 k

假設各次取樣彼此獨立、單次答對機率固定為 p，則 k 次中至少一次答對的機率是 1−(1−p)k。這是示意計算，不是某份benchmark的實測值。

課堂上展示的對比是同一件事：Llama 3（8B、70B）與 Gemma 等開放模型單次作答輸給 GPT-4o，但取樣數一路拉高之後，它們的 coverage 就能追過大模型的單次表現。橫軸是取樣數（投影片從 1 拉到 1,000），縱軸是資料集層級的 coverage，曲線呈現近似 log-linear 的上升——等於在推論階段也看到了一條 scaling law。

要留意

取樣不是免費的

每一次取樣都是一次完整的推論呼叫。評估取樣策略時，除了準確度，還要把運算預算與回覆品質一起算進去。

要留意

曲線終究會平

取樣再多，也碰不到模型永遠生不出的答案。重複取樣擴大的是候選集合，不是模型的能力上限。

03

難題長尾：為什麼整體是 power law

▶ 00:09:23
一句話重點

單題的成功率是指數型，資料集看到的卻是冪次型。講者說，讓這件事成立的「充分且必要條件」就是題目難度有一條長尾。

這是本講最容易被跳過、卻最值得停下來的一節。上一節的 1−(1−p)k 是單一題目的行為：快速上升，然後飽和。但把一整個資料集畫在同一張圖上，曲線並不會一起飽和，而是像對數一樣一路往上爬，也就是 power law。這兩件事要能同時成立，題目難度的分布必須很特別：

  • 大部分題目很容易：pass@1 很高，一兩次取樣就解出來，曲線一開始衝得很快。
  • 少數題目非常難：pass@1 低到 1% 以下，需要幾百、幾千次取樣才偶爾出現正解，它們負責把曲線的右半邊拉得很長。
  • 把這兩群加總，就得到你在論文中看到的那條「再多取樣 10 倍，就多升一點」的曲線。

動手試試：長尾如何變成冪次型曲線

左圖把題目依難度分成幾組（柱高＝該組題目佔的比例），右圖是把各組的 1−(1−p)k 加權加總後的整體 coverage。分組與成功率都是示意值，重點在於「只要尾部夠長，曲線就不會飽和」。

課堂上展示的實測圖也是同一件事：把題目按 pass@1 由高到低排，會看到一大群題目集中在高 pass@1 的左側，右側則拖出一條又長又低的尾巴。講者強調，各題難度分布才是理解整體 scaling 的關鍵——曲線本身只是這個分布加總後的結果。

實務上意味著什麼：如果你的任務裡幾乎都是容易題，重複取樣很快就沒有效率（曲線早就平了）；如果任務本身就在模型的困難區，取樣才值得投入。同一筆預算，換一個資料集，報酬可能完全不同。

Verifier：哪些任務能自動驗證

▶ 00:12:19
一句話重點

取樣只解決「有沒有碰到正解」，verifier 才決定「有沒有拿到正解」。能自動驗證的任務，取樣才直接換成準確度。

一旦有了幾百個候選，問題就變得非常具體：我要選哪一個？如果沒有可靠的判斷方式，增加樣本數只是讓問題變大，沒有讓答案變好。課堂列了四種可驗證的情境：

AI as a compiler：把「翻譯」變成可驗證的任務

講者花了一段時間介紹實驗室的一個方向：讓 LLM 把高階的 PyTorch 程式轉成低階的 CUDA kernel。CUDA 是更貼近硬體、可以針對 GPU 效能最佳化的語言，所以這個轉換本身就有實務價值。但更重要的是——它剛好是可驗證的：

為什麼有效

驗證比生成容易

在某些任務裡，設計一個能抓出錯誤的測試，比直接寫出完整解答更容易。測試因此可以取代人類，成為不知疲倦的 verifier。

KernelBench

可執行測試的程式任務

課堂展示 KernelBench 這個 CUDA 生成基準：因為預設就能用測試判定正確性，取樣數增加時 coverage 穩定上升，取樣與驗證可以直接搭配使用。

但這是容易的那一半。數學證明、程式測試這類任務有現成的客觀檢查；開放式寫作、摘要、建議這類任務沒有。下一節就是講沒有 verifier 的時候會發生什麼事。
05

Generation–Verification Gap

▶ 00:15:33
一句話重點

模型「能生成」正解，不代表系統「能拿到」正解。兩者之間的落差，就是 generation–verification gap。

把三條線畫在同一張圖上就清楚了：一條是假設有完美驗證器時可達到的 coverage，另外兩條是實際可用的選擇方法——majority voting（多數決）與 reward model 打分後取最高。課堂的觀察是：多數決大約在 10～50 個樣本之後就停住了，而 coverage 還在往上走；題目越難，這個口子越大。

coverage 與多數決的落差

示意曲線：依課堂描述的趨勢重繪（多數決在 10～50 個樣本後停滯、MATH 比 GSM8K 更難），不是投影片上的實際數值。藍線是假設完美驗證器可達的 coverage，橘線是多數決實際拿到的準確度。

為什麼多數決會失效

多數決把出現頻率最高的答案當作答案，所以它仰賴正解在候選中重複出現。問題就在這裡：對最難的那批題目，模型在 1,000 甚至 10,000 個樣本裡，可能只解出一、兩次。正解存在，但頻率太低，多數決永遠選不到它。

示意：100 個樣本裡，多數決看到了什麼

切換兩種題目，看多數決各自會選到什麼。格子配置是示意，用於說明頻率這個關鍵變因。

正確答案的樣本 出現最多次的錯誤答案 其他錯誤答案

名詞

Generation–verification gap

生成端可以做得很強，驗證端卻跟不上，於是系統真正能利用的正解遠少於已生成的正解。Verifier 的能力，決定了你能把多少 coverage 轉換成準確度。

核心研究問題

正解很稀少時，怎麼找到它？

這是講者留給學生的題目，也是本講後半段的主線：既然正解稀有、又認不出來，那就要更聰明地分配算力，而不是無腦多取樣。

Verifiers 本身也會錯。有學生追問 coverage 的數字到底可不可信——通過測試不等於答案正確。講者回應，數學那批資料曾人工抽查，正確率落在 90% 多（字幕在此處不清楚，無法給出確切數字）；但如果 unit test 沒有真正覆蓋到程式的行為，這就是一個失敗模式。驗證器的品質，永遠是這條鏈上最弱的一環。

第二條路徑：Sequential Revision 與 PRM

▶ 00:26:53
一句話重點

除了平行多問幾次，還可以沿著同一條解一路改。PRM 讓你在中途就判斷這條路好不好，於是預算花在值得繼續的地方。

兩種 reward model：看結果，還是看過程

ORM

Outcome reward model

替最終答案打分。搭配平行取樣，就是生成多個候選、取分數最高的那個（best-of-N）。缺點是換到新領域時，評分準確度可能明顯受限。

PRM

Process reward model

替解題過程中的步驟打分，讓系統比較不同解題路徑的中間品質，而不只是看最後結果。

PRM 怎麼引導搜尋：beam search

課堂用一個預算為 4 的例子說明。點選各步驟查看。

關於 PRM 有兩個常被誤解的點，課堂特別澄清。第一，PRM 的分數通常對應一個有意義的推理步驟或片段，不是逐 token 打分；步驟的單位可以是句子，或其他智力上有意義的區塊。第二，訓練資料通常來自人工標記每一步的好與壞，再依此訓練；因為 PRM 本質上是語言模型，它能大致泛化，但在與任務同分布（in-domain）時表現明顯比較好。

兩種可以立刻用的做法：市面上已有不少現成的預訓練 PRM，可以直接拿來引導你自己任務上的搜尋，先挑一個與任務最相關的試用；如果手上有資料，也可以自己訓練 ORM 或 PRM。

真正的重點是「組合」

把平行取樣、序列修訂與 reward model 結合，通常比只用其中一種更好。論文中一個很簡單的組合方式是：先平行取樣，讓每個平行候選各自做幾次序列修訂，最後再用 PRM 或 ORM 從中排序選出答案。PRM 也可以在修訂流程中逐步引導搜尋方向。至於在有限 token 預算下，兩者各該分配多少才算最佳化——講者明確說，這仍是尚未解決的研究問題。

另一個更尖銳的發現：test-time 不是萬能

同一篇論文比較「增加 pre-training」與「增加 test-time FLOPs」，結論依難度分成兩種世界：

容易題與中等題

追加推論算力比較划算

以 token 效率來看，追加 test-time compute 通常比再擴大 pre-training 更有利。這正是開源模型與較小模型變得更實用的原因：它們可以靠更多推論算力補上一段差距。

最難的題目

更大的基礎模型仍然勝出

對最難的那批題，即使給推論預算很大的額度，仍然是 pre-training 更多、規模更大的前沿模型表現較好。講者補充：當然我們沒有無限預算，但即使給到相當大的額度，這個結論依然成立。

「但 pre-training 只付一次啊？」有學生這樣追問。講者的回應是：沒錯，pre-training 一次、inference 每次都要付，但兩者不是一比一的相同成本，評估時要把使用頻率與預算一起放進來。而且即使擴大 pre-training 昂貴到不是人人都負擔得起，它依然重要——只是對多數任務而言，直接追加 test-time compute 是更容易取得、可以按需投入的那個槓桿。

Archon：讓系統自己設計推論流程

▶ 00:45:38
一句話重點

與其手動試各種組合，不如把「推論流程本身」當成搜尋對象：在呼叫預算的限制下，讓最佳化器找出該用哪些模型、疊幾層操作。

前面幾節留下了一個工程上很煩的問題：模型有很多個、推論操作也有很多種，到底該怎麼搭配？Archon 的做法是把這件事定義成一個搜尋問題，稱為 ITAS（Inference-Time Architecture Search）：輸入可用的模型、可選的推論操作、目標基準與呼叫預算，輸出在預算內表現較好的架構。

七種可組合的推論操作

生成

Generator

對輸入問題產生 N 個不同回覆，也就是重複取樣。

合成

Fuser

把 K 個回覆連同原問題一起交給模型，請它綜合出一個新答案，而不是從中挑一個。

批評

Critic

對任一回覆指出優點與缺點，作為後續步驟的依據。

排序

Ranker

請模型依品質替上一產出的回覆排序。這些操作都是純 prompt 的，模型並沒有為這個任務被訓練過。

驗證

Verifier

回覆判斷結果，同時說明為什麼給這個分數。

測試

Unit test generator

先產生測試，再拿來檢查生成的程式。

評估

Evaluator

在 held-out 資料上量測準確度與呼叫成本，作為最佳化的目標。

Fuser 為什麼能贏過「完美驗證器」

課堂展示了一個問答推理基準上的比較（左圖是單一模型重複取樣，右圖換成多個模型的 ensemble，趨勢相同）。取樣數從 1 到 10，由差到好大致是這個順序：

  • 隨機挑一個
  • →
  • 請模型排序，取第一名
  • →
  • Oracle selection：假設有完美驗證器，直接挑出正解
  • →
  • Fusion：把 K 個回覆交給模型合成一個新答案
  • →
  • 先排序取前 5，再融合

這裡有個反直覺的重點：融合可以贏過 oracle selection。因為 oracle 只能在既有候選中「挑一個」，而 fuser 讀完所有候選後產出一個原本不在候選裡的新答案——它不受候選集合的上限約束。先過濾再融合效果更好，說明「篩掉雜訊」與「整合資訊」是兩種不同的收益。

Unit test 也可以由模型生成

在程式任務上，模型除了生成程式，還可以先產生 unit tests，之後再執行、或由模型依測試評估候選程式。課堂舉了一個括號配對的題目：

程式題目檢查輸入字串中的小括號是否成對
測試 1若字串中括號的總數是奇數，解法應回報不合法
測試 2遇到右括號時，必須配對最近一個尚未被配對的左括號
下一步請模型依這些測試產生程式，再檢查是否通過生成＋驗證

測試內容依課堂口述改寫，用於說明「把需求寫成可檢查條件」這件事。講者還提到一個更「瘋狂」的變體：不真的執行測試，而是請模型評估一個答案是否符合這條測試。

一個有趣的發現是：疊越多層推論操作，準確度還會再上升。講者把它類比成深度學習裡疊層——只是這裡疊的是 critic、ranker、fuser 這些推論層。實驗中最右邊那組是 ensemble（迴圈中使用不同模型）加上三層批評與融合、再接一層最終融合，在多數任務上都明顯勝過「只用最好的模型跑一次」或「最好的模型跑八次加一層融合」。

怎麼在爆炸的搜尋空間裡搜尋

  1. 先做前置處理，限制順序搜尋很貴，因為每個配置都要跑大量推論呼叫。團隊先離線找出「generation → critic → ranker → fuser」這組順序本身就表現很好，把它固定下來。
  2. 加上結構性限制第一層永遠是 generator；critic 一定要排在 ranker 或 fuser 之前，讓後續步驟能用批評結果來評選或整合；結尾接一個 evaluator。
  3. 用 Bayesian optimization 探索比貪婪搜尋或隨機搜尋更省樣本——評估較少的配置就能收斂。目標函數可以設定成可用的模型集合與推論呼叫預算。
  4. 在 held-out 資料上量測最佳化的指標是「準確度 vs. 呼叫次數」：在給定預算下把準確度最大化。
結果：投影片報告，Archon 只使用開源模型，就能在 instruction following、reasoning 與 coding 等任務上，pass@1 平均改善 14.1%（基準為投影片所列的 GPT-4o、Claude 3.5 Sonnet 等前沿閉源模型）。此外它還能被訓練成任務專用的版本，而即使是通用版也在這些任務上勝過前沿模型——這意味著推論架構的設計本身，可以帶來超出單一任務的泛化。這個 14.1% 是該研究所選資料集、模型與設定下的數值，解讀時要連同設定一起看。

課堂問答精選

這堂課有兩段學生討論。學生的發言往往正好打在最容易混淆的地方——例如「coverage 的數字可信嗎」、「pre-training 只付一次怎麼比較」。先自己想一下答案，再展開對照。

能不能把這些觀察從特定 benchmark 推廣到更一般的領域，讓模型逐輪修訂自己的解答？

這正是下一節的主題。把解法從「只在這個資料集上有效」推向更一般的做法，其中一條路就是讓模型在每一輪檢查並改寫自己的答案，直到它認為足夠好才輸出——也就是 sequential revision。

可以混合檢索與取樣嗎？例如先做 retrieval，只有檢索結果不夠好時才開始取樣。

有學生提出這個混合做法：搭配文件做檢索，當檢索分數低於門檻、準確度不足時才訴諸重複取樣，因為檢索本身也花時間。講者認同這個方向，並釐清兩者的角色：檢索有助於效率、能降低對取樣的依賴，但不能取代準確度本身。

如果先讓模型「自學」這個領域、蒐集洞見，之後再進入平行取樣，pass@k 會不會更好？

這是學生提出的假設：在取樣之前先加一個探索階段，讓模型把領域知識整理好，再 funnel 進平行取樣。講者回應，這屬於「重複取樣之外如何改進 test-time scaling」的一類方法，課程後續會談 self-study、搜尋與 tool use。

Verifier 本身不準怎麼辦？例如驗證要靠模擬器，而模擬器也是個模型。

講者承認這是真實的問題（他形容驗證有時是「模糊的」），並給出實務方向：可以用模擬器、其他工具，或另一個模型來過濾錯誤答案，具體做法端看領域。另外，把多個 verifier 的判斷做多數決也是一個方向——講者提到課程後續會談整合一小群 verifier（十到二十個，而不是上千個）的工作，但那個方向從運算角度來看成本很高。

Coverage 的數字可信嗎？通過測試不等於答案正確。

這是本堂課最尖銳的一問。講者的回應是：數學那批資料曾人工抽查已答對的題目，正確率落在 90% 多（字幕在此處不清楚，無法給出確切數字）。但他同時承認這是永遠存在的失敗模式——如果你的 unit test 沒有真正覆蓋程式的行為，coverage 就會灌水。結論是：verifier 的品質本身必須被審查。

Pre-training 只付一次，inference 每次都付，這樣比較兩者公平嗎？

有學生指出這個不對稱。講者同意 pre-training 確實是一次性的、而 test-time scaling 每次執行都要付，但強調兩者不是一比一的相同成本；評估時要把使用頻率與預算一併考慮。他也補充了現實面：即使擴大 pre-training 比較有效，那也不是人人都負擔得起的選項，而 test-time compute 對多數任務而言是可以按需取得的。

那能不能把小模型針對某組題目特別訓練，讓它變強？

可以——針對特定題庫訓練，小模型確實能被專門強化。但講者區分了比較的口徑：課堂談的是在通用資料、通用訓練配方下比較模型能力，而不是為考題量身定做。

容易題和難題，推論預算該怎麼分？

討論中形成的直覺是：容易題任一條路都可能通往正解，因此不必平行探索多條解，比較適合在同一個候選上持續修訂；難題則需要更多平行探索。講者把這件事講成一個清楚的框架：把生成的 token 當成一個可以轉的旋鈕，問題是如何依任務分配它，以及如何讓模型把這些生成用在對的地方。

這些取樣資料集可以拿到嗎？

講者提到，課堂展示的資料集——每題最多 10,000 個不同取樣——公開在 Hugging Face 上，有興趣的人可以拿去研究如何改進 generation–verification gap。他說這可能成為一門不錯的課程研究專案。

一頁總結

  1. 算力可以搬到推論階段：參數完全不動，只改變生成與挑選的方式，就能顯著提升表現；而且這筆開銷可以按需、逐題投入。
  2. 重複取樣的算術：單題至少一次答對的機率是 1−(1−p)k。要補上 10% 的單次成功率，需要指數成長的取樣次數。
  3. 冪次律來自長尾：單題是指數、資料集是冪次，因為題目難度有一條長尾；尾部那些題把曲線右半邊拉長，讓 coverage 看起來永不飽和。
  4. 瓶頸在驗證，不在生成：多數決在 10～50 個樣本後停住，coverage 卻還在升；這個落差就是 generation–verification gap。最難的題，正解在上萬個樣本裡只出現一兩次。
  5. 兩條路徑要合著用：平行取樣擴大多樣性，序列修訂深化單條解；PRM 對步驟打分、引導 beam search，讓預算花在值得繼續的路徑上。
  6. 難度決定配置：容易題偏序列修訂、難題偏平行探索，最難的題沒有通用最佳比例；而且最難的題仍然由更大、pre-training 更多的模型勝出。
  7. 流程本身可以被搜尋：Archon 用 Bayesian optimization 在呼叫預算內組合模型與推論操作；融合能贏過完美驗證器，疊更多推論層還能再提升準確度。
